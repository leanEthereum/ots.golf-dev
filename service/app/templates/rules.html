Rules

What is a one-time signature?

A one-time signature (OTS) uses a key pair to sign one message securely. This competition is about hash-based OTS, whose security rests on a hash function alone. For examples, see Lamport signatures, which reveal selected secrets, and target-sum Winternitz signatures, which use hash chains.

What are we optimizing?

We fix a budget for the public-key size, signature size, security, key generation and signing, and try to minimize the verification cost:

Fixed requirements and the verification objective
ParameterRequirement
Public key128 bits
Message256 bits
SignatureAt most 5,504 bits
Key generationAt most 1,024 compressions
SigningAt most 220 compressions
Security127 bits
VerificationMinimize the worst-case cost{% if upper_riscv_track %}, in compressions or RISC-V cycles{% endif %}

Every track requires a Lean-kernel-checked proof.

Upper bounds

Construct a provably secure hash-based OTS and prove an upper bound on its worst-case verification cost. Any oracle algorithm is allowed, as long as it satisfies the requirements above. Smaller claims are better.

  • By compressions. The cost is the number of hash compressions.
    • {% if upper_riscv_track %}
  • By RISC-V cycles. Implement the verifier in RISC-V, prove it computes exactly the Lean verifier, and bound the cycles of every execution, accepting or rejecting.
    • {% endif %}

Lower bounds

Prove that every admissible OTS in a class needs at least the claimed worst-case verification cost, in compressions. Larger claims are better. Given the difficulty of the problem, we define three classes of increasing generality, each with its own record.

  • Generality 1/3. DAGs built from whole 128-bit words: secrets, fixed public words, hashes, hash halves and concatenation.
  • Generality 2/3. A DAG with arbitrary functions.
  • Generality 3/3. Any oracle algorithm.

Upper bound and lower bound with Generality 3/3: any algorithm

A scheme consists of three terminating oracle programs: key generation, signing and verification. Key generation and signing may use private randomness; verification is deterministic. Whenever honest signing returns a signature, verification accepts with probability one. Signing may fail, but only with probability at most 2−128, for any message.

Signatures are bit strings. Every possible signer output has at most 5,504 bits, and verification rejects longer strings. A compression claim bounds the verifier's cost on every input, whether it accepts or rejects.

{% if upper_riscv_track %}

RISC-V upper bound

Submit an OTS meeting the algorithm requirements above, together with a fixed RV64IM verifier. Prove that its execution implements the Lean specification: the same oracle computation and decision for every public key, message and raw signature bit string. Every execution must terminate, including malformed and rejected inputs.

The claim bounds cycles on every execution, accepting or rejecting, for every input and oracle answer. Each ordinary instruction and the halt cost one cycle. The HASH call costs max(1, ⌈n / 512⌉) cycles for an n-bit input, with no additional instruction charge. It uses the same random oracle as the OTS security experiment.

Lower bound · Generality 2/3: DAGs

The scheme is described by a public directed acyclic graph (DAG). Each node holds one value, a bit string of fixed length, and comes in one of three kinds: a source holds a fresh uniform random string, a deterministic node holds any fixed function of its parents' values, and a hash node holds the hash of its single parent's value. Parents come before children, and a value may feed several nodes. Key generation draws the sources, evaluates every node once and stores all the values; the public key is the low 128 bits of the root hash.

A signature reveals a cut: stored values meeting every source-to-root path, excluding the root. Verification follows all declared parent edges backwards to the cut, then evaluates required nodes forwards, once each.

  1. Select a cut. The scheme supplies 2115 indexed cuts. Read the low 128 bits of H(message ‖ nonce) as an integer; it is valid below 2115. Try up to 220 uniformly sampled 128-bit nonces without replacement, stopping at the first valid index or failing.
  2. Reveal. Send the nonce and the cut's node values in node order, with at most 5,376 payload bits.
  3. Verify. Reject invalid indices or wrong payload lengths; otherwise reconstruct the root and compare its low 128 bits with the public key.

The score is the maximum over all indexed cuts: one compression for the message-and-nonce query, plus the costs of reconstructed hash nodes.

Lower bound · Generality 1/3: whole words

This class keeps the DAG model of Generality 2/3 (key generation, cuts, signing and verification are unchanged) and restricts what the nodes may compute to whole 128-bit words. Each source is one uniform word, and each hash returns 256 bits. A deterministic node may do only three things: output a fixed public word, take the fixed low or high half of a hash output, or concatenate complete earlier values, in any order, with repetitions or grouping, possibly none. As before, a value may feed several nodes.

How do I submit a proof?

Submit an upper-bound construction, or a lower-bound proof for one of the three classes.

  1. Read the notes of earlier submissions: their ideas, results and dead ends.
  2. Fork the submissions repository and follow its setup instructions. Create or change one submission root: formal/Submissions/LowerGenerality1/, formal/Submissions/LowerGenerality2/, formal/Submissions/LowerGenerality3/, formal/Submissions/UpperCompressions/ or formal/Submissions/UpperRiscv/.
  3. Put your claim in claim.txt and export the required declarations from Solution.lean. Add a NOTES.md beside them: the idea, the result, what did not work and what you would try next.
  4. Run python3 .contract/verifier/verify.py lower-generality-2 --source . (or lower-generality-1, lower-generality-3, upper-compressions or upper-riscv), then open a pull request to the submissions repository. Its author and description supply attribution; optional Assisted by: and Co-authors: lines credit collaborators. Each new head is rechecked. A verified strict improvement is merged automatically and becomes the record.

Submissions that do not beat the record are welcome too, and so are attempts that fail: their notes join the journal, and every checked head stays fetchable from the submissions repository, so others can build on it.

How are submissions checked?

Use a flat root: identifier-named .lean files, claim.txt, optional README.md and NOTES.md, and required Solution.lean. The claim is an integer from zero to {{ cfg.limits.max_claim|int }}, without leading zeros and with at most one trailing newline. Import only Mathlib, VCVio, permitted contract modules and siblings. Use the pinned toolchain and dependencies; submissions cannot alter protected definitions.

The verifier checks the exact claim and exported declarations. No sorry or extra axioms: only {{ cfg.permitted_axioms|join(', ')|safe }}. native_decide introduces an unpermitted axiom. Limits: {{ cfg.limits.max_files }} files, {{ cfg.limits.max_file_bytes // 1048576 }} MiB per file, {{ cfg.limits.max_total_bytes // 1048576 }} MiB total, {{ cfg.limits.wall_clock_seconds // 60 }} minutes, {{ cfg.limits.memory_bytes // 1073741824 }} GiB and no network.

The core repository defines the model and verifier: constants and oracle, generic interface and statements, DAG contract, whole-word condition, verifier configuration and submission specification.
